AG-UI × KurrentDB middleware

A from-zero walkthrough: what the problem is, what the middleware does, and why a single 200-line piece of TypeScript gives every AG-UI-compatible framework durable, replayable, cross-framework conversations.

1. The problem 2. Two protocols, two layers 3. The middleware 4. Walkthrough 5. Cross-framework 6. Why it matters

1. The problem

You build an AI agent. A user opens a chat UI, asks "What's the weather in Oslo?", the agent calls a tool, gets a result, replies. So far, so normal.

sequenceDiagram autonumber participant U as User (browser) participant A as Agent backend participant T as Tool U->>A: "Weather in Oslo?" A->>T: get_weather({city:"Oslo"}) T-->>A: {temperature_c:8, condition:"light_rain"} A-->>U: "8°C with light rain in Oslo."

Now the conversation ends. Where did all of that go?

  • Did you log it for audit / compliance?
  • Can the user resume the conversation tomorrow?
  • Can a different agent framework pick up where this one left off?
  • Can you replay it for an evaluator to score?

Out of the box: no. Wiring durable storage, deciding the schema, handling resume — that's all on you.

2. Two protocols, two layers

Two open standards already exist for the parts of this we care about — and they live at different layers:

LayerStandardJobLifetime
Wire AG-UI Protocol How an agent talks to a UI in real time. Streaming text, tool calls, state. Ephemeral — events fly past, then are gone.
Durable record KurrentDB canonical schema How an agent session is stored: a stream of typed events you can replay. Append-only, forever.

Insight: AG-UI events and canonical KurrentDB events are talking about almost the same things — a user message, an assistant reply, a tool call, a tool result. They differ only in granularity: AG-UI streams a message in many pieces (start, content delta, content delta, end); the canonical schema records one event per finished message. That match is what makes a clean bridge possible.

3. The middleware

AG-UI's @ag-ui/client ships a Middleware base class. You can wrap any AG-UI agent and observe everything it emits before the events reach the UI:

graph LR classDef store fill:#f1faf3,stroke:#15803d,color:#114b25 classDef mw fill:#fff4e6,stroke:#b45309,color:#5c2e00 A["AG-UI agent
LangGraph · Mastra · ..."] M["KurrentDBMiddleware
~250 lines of TypeScript"]:::mw UI[UI / consumer] DB[("KurrentDB
AgentSession-...")]:::store A -->|emits AG-UI events| M M -->|passes through unchanged| UI M -->|appends canonical events| DB

Two things matter:

  • Pass-through. The middleware doesn't change what the UI sees. Your existing AG-UI client keeps working.
  • Single implementation, many frameworks. AG-UI is the wire format. Anything that emits AG-UI events — LangGraph, Mastra, CrewAI, MS Agent Framework, Google ADK, Claude Agent SDK — gets durable storage by adding one line: agent.use(new KurrentDBMiddleware({ client })). That's the lever.

4. Walkthrough — a weather query, end to end

Same conversation as §1. Here's what actually happens on the wire and on disk.

4.1 What the agent emits (AG-UI, ~15 events)

AG-UI streams every message in pieces. A 4-message conversation produces ~15 events:

RUN_STARTED            thread=demo run=run-001
TEXT_MESSAGE_START     id=u1 role=user
TEXT_MESSAGE_CONTENT   id=u1 delta="What's the weather in Oslo?"
TEXT_MESSAGE_END       id=u1
TEXT_MESSAGE_START     id=a1 role=assistant
TEXT_MESSAGE_CONTENT   id=a1 delta="Looking that up."
TEXT_MESSAGE_END       id=a1
TOOL_CALL_START        id=c1 name=get_weather parent=a1
TOOL_CALL_ARGS         id=c1 delta='{"city":"Oslo"}'
TOOL_CALL_END          id=c1
TOOL_CALL_RESULT       id=c1 content='{"temperature_c":8,"condition":"light_rain"}'
TEXT_MESSAGE_START     id=a2 role=assistant
TEXT_MESSAGE_CONTENT   id=a2 delta="8°C with light rain in Oslo."
TEXT_MESSAGE_END       id=a2
RUN_FINISHED           thread=demo run=run-001

4.2 What the middleware observes

sequenceDiagram autonumber participant Ag as Agent participant MW as Middleware participant DB as KurrentDB Ag->>MW: RUN_STARTED MW->>DB: append SessionStarted Note over MW: read AgentSession-demo tail
(empty, first run)
seed messageId dedup Ag->>MW: TEXT_MESSAGE_START/_CONTENT/_END (u1, user) Note over MW: observe — no append yet Ag->>MW: TEXT_MESSAGE_START/_CONTENT/_END (a1, assistant) Note over MW: a1 looks like text-only... Ag->>MW: TOOL_CALL_START/_ARGS/_END (c1 → parent=a1) Note over MW: ...but a1 just got upgraded
to text + tool call!
Defer until RUN_FINISHED. Ag->>MW: TOOL_CALL_RESULT (t1, role=tool) Ag->>MW: TEXT_MESSAGE_START/_CONTENT/_END (a2, assistant) Ag->>MW: RUN_FINISHED Note over MW: now flush:
each AG-UI message is in final form MW->>DB: UserMessageReceived (u1) MW->>DB: AssistantToolCallsGenerated (a1) MW->>DB: ToolResultReceived (t1) MW->>DB: AssistantTextGenerated (a2) MW->>DB: SessionEnded

Why defer to RUN_FINISHED? AG-UI can upgrade an assistant message: emit a text message, end it, then later attach a tool call to it via parentMessageId. If the middleware persisted at TEXT_MESSAGE_END, it would write AssistantTextGenerated for a1 — then have no way to upgrade it to AssistantToolCallsGenerated when the tool call arrives, because the canonical schema is append-only. Deferring sees the final form. Trade-off: no partial durability if the host process dies mid-run; aborted runs are flushed explicitly.

4.3 What's in KurrentDB afterwards (6 canonical events)

#Event typePayload (abridged)
0SessionStartedapp_name=weather_demo, agent_name=Weather, model=…
1UserMessageReceivedid=u1, content="What's the weather in Oslo?"
2AssistantToolCallsGeneratedid=a1, content="Looking that up.", tool_calls=[{call_id:c1, tool_name:get_weather, arguments:{city:"Oslo"}}]
3ToolResultReceivedcall_id=c1, result='{"temperature_c":8,"condition":"light_rain"}'
4AssistantTextGeneratedid=a2, content="8°C with light rain in Oslo."
5SessionEndedreason=complete

Every event also carries metadata: $schema_version=2 and $run_id=run-001. The $run_id is what lets evaluators score per-run, not just per-session.

15 ephemeral wire events → 6 durable typed events. No information lost; conversation reduced to its message-level essence.

5. Cross-framework portability

Here's where the canonical schema earns its keep. The middleware writes TypeScript-side; any reader in any language can consume the same stream because they all share schema/proto/kurrent/agent/v2/*.proto:

This isn't theory. The acceptance test in ag-ui/interop-tests/ proves it:

  1. Spawn the TS middleware writer (npm run interop:write).
  2. It runs a synthetic AG-UI agent and writes 6 canonical events to KurrentDB.
  3. Python KurrentDBHistoryProvider.get_messages() — the production reader code from the MS Agent Framework integration — reads the same stream.
  4. Assert: Message[] reconstructs with the right roles, text, function_call blocks (name, call_id, arguments), and function_result blocks (call_id, result).

The middleware doesn't import MAF; MAF doesn't import the middleware. The canonical schema is their only contract — and it works.

6. Why this matters

One TypeScript implementation × every AG-UI integration.

AG-UI today has integrations for ~15 frameworks. Without this middleware, persisting any of them to KurrentDB requires a per-framework adapter. With this middleware, every existing AG-UI integration gets durable, replayable, cross-framework-portable session storage by adding one line to the agent setup.

What you get for free, per framework

  • Durability. Sessions survive process restarts, crashes, redeploys.
  • Resume. Same threadId next run → middleware reads the prior history, dedupes, picks up where it left off.
  • Replay / audit. Walk any past session event-by-event for compliance or debugging.
  • Eval-ready. Every event tagged with $run_id; evaluators can score per-run.
  • Cross-framework reads. A session written by one framework can be read by another's tooling — proven by the MAF reader interop test.
  • Capacitor UI. Kurrent's session-browsing UI works on any AgentSession-* stream; no framework-specific code needed.

The minimum to use it

import { KurrentDBClient } from '@kurrent/kurrentdb-client';
import { KurrentDBMiddleware } from '@kurrent-io/ag-ui-middleware-kurrentdb';

const client = KurrentDBClient.connectionString(
  'kurrentdb://localhost:2113?Tls=false',
);

const agent = new MyAGUICompatibleAgent();
agent.use(new KurrentDBMiddleware({ client, appName: 'my-app' }));

await agent.runAgent({ runId: 'run-001' });
// AgentSession-{threadId} now contains the full canonical history,
// readable by every Kurrent integration in the monorepo.
